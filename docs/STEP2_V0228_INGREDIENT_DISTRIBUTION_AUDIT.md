# STEP 2 v0.2.28 — 整数食材バッグ・料理成立確率の独立分岐カーネル監査

日付：2026-10-17 JST。**STEP 2計算精度ゲートHOLD。STEP 3未着手。**

## 精度問題の切り分け
現行週間エンジンは個体所持数・きのみ/食材・スキル発動履歴・共有食材バッグを期待値で集計する部分が残り、`inventory.apple = 7.5` のような食材期待個数が存在する。これを「リンゴ7個を確実に持っている」「成立確率が100%」に読み替えることはできない。**期待値しかないデータから食材種類別の同時確率分布は数学的に一意に復元できない。**

## 実装
`src/ingredient-distribution.js` が追加提供する、ゲーム入力値とは独立した3個の純粋な計算API：
- `certainIngredientBag(initialStock,capacity)` — 確定初期在庫（食材19種、個数は整数）から質量1の分布を生成。
- `addIngredientOutcomes(distribution, outcomes, capacity, maxStates)` — 与えられた**相互排他的な**食材抽選の正確な結果確率から種類別整数在庫の状態遷移を構築。バッグの空きは各分岐で計算し、`expectedAdded` / `expectedRejected` を返す。ひとつの抽選は0個または**1種類の食材**を獲得するものとする。
- `evaluateRecipeOutcomes(distribution, requirements, capacity, maxStates)` — すべての必須食材の整数個数が揃う分岐だけ材料を消費し、料理成立確率と消費後の共同在庫分布を返す。未成立の分岐で材料を消費しない。`expectedConsumed` は成功確率を掛けた必要数である。

確率質量は合計1を検証。分布キーの種類・整数・規格化・バッグ容量に不備があればエラーで停止。最大4096状態を超えても確率を切り落としたり、期待値計算に黙って戻したりしない。食材バッグ容量0は既存シミュレーターと同じく「容量指定なし」。

## 独立境界（計算式のオラクル）
空バッグに「リンゴ8個 50%、ミルク8個 50%」の互いに排他的な抽選が1回あるとき：
- 必要リンゴ7個の料理成立率は50%。
- 必要リンゴ7個・ミルク7個の料理成立率は0%（期待数リンゴ4/ミルク4だからといって食材が同時に揃うわけではない）。
- 成立した分岐だけリンゴ7個を消費し、残量リンゴ1個 50%、ミルク8個 50%。
- バッグ容量5・初期リンゴ4の場合、2個または3個の追加抽選は各枝1個のみ受領し、超過分は枝ごとに算出する。
- 逐次抽選と料理を繰り返しても、成立しない枝は材料を消費しない。

## 回帰
12件の専用オラクルで、初期1状態・確率的な食材種類・同時材料・逐次抽選・バッグ溢れ・食材0・不成立の不消費・複数料理・19種類の識別・入力拒否・分岐爆発拒否・総確率保存を確認。追加でブラウザー起動テストが新モジュール同梱を確認する。

## 境界・残課題
- **週間エナジーエンジンにはまだ結合しない。** 毎15分の各ポケモンのおてつだいで生じる食材種類別の分布、スキル抽選・個体所持制限・回収順序・他ポケモンとの相関が正確な入力として揃う前に結合すれば、誤った料理成功確率を提示するため。
- 食材ゲットの複数種類同時排出・ボックスのキュー遷移・不規則な複合スキルについては、「1抽選で1種類」以外の結果の扱いを次段階で独立拡張する必要がある。
- バッグ上限では食材を取得できなかった分を「拒否」として数えるが、個体のポケットに残す正確な処理・集約は別の週間モデルが担う。
- 実ゲーム週次の定量比較、Android Chrome実機での操作と速度は未実施。
- 初期確定在庫に対し単独の抽選結果確率が**正確に与えられている時だけ**結果が数学的に正しい。ゲーム全体の精度改善を主張しない。

**結論：食材同時分布と料理成否の計算基盤を検証可能な単位に分離した。STEP2精度HOLDを維持する。**

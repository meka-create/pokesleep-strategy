# M1/M2：料理の食材充足と鍋容量の確実性を区別する（v0.2.60）

## 再現した問題・優先度

P1：食材が初期在庫だけで揃うことから、料理のレシピ選択・追加投入量まで独立比較可能と誤認する診断漏れ。
週間本体はスキル発動回数の期待値を鍋拡張へ加算し、丸めた容量で料理を選ぶ。
容量の分布や不発動分岐を解決していないが、従来の観測比較は食材由来の不確実性だけを確認していた。

再現入力は `tests/step2-pot-dependency.test.cjs` の `input()`。
ジバコイル1匹＋ライチュウ4匹（Lv50・スキルLv6・まじめ・サブスキルなし）、同一5匹を全時間帯に固定。
初期食材トマト210・ハーブ105、バッグ500、鍋7、固定サンパワートマトカレー、追加食材・大成功OFF、
ゴールド旧発電所・25%、睡眠88・初期げんき100、回収150分。

独立した容量算術：レシピ必須量10＋5＝15個。スキルなしの通常鍋7個、日曜14個とも15未満。
初期食材は21食分あるが、全てのレシピ成立は鍋拡張が必要。この論理はゲームの発動確率を仮定しない。

| 指標 | 修正前 | 修正後 |
|---|---:|---:|
| 計上料理数 | 20 | 20 |
| 初期食材充足食数 | 20 | 20 |
| 生産期待値依存食数／追加食材含む依存食数 | 0 / 0 | 0 / 0 |
| 料理エナジー（モデル値） | 185,960 | 185,960 |
| 鍋拡張依存食数 | 未記録 | 20 |
| 確認フラグON時の観測分類 | UNCALIBRATED_OBSERVATION | CONFOUNDED_OBSERVATION |

185,960はモデル出力であり実ゲーム記録ではない。ゲーム誤差量・週次順位の逆転を実証した数字ではない。

## 修正範囲

- 食事ごとにスキル拡張0の容量を既存の日曜／キャンプ規則で求め、同じ食材在庫でレシピ選択を再照合。
- レシピ選択が変わる、または実際の計上投入個数が基礎容量を超える場合、`potDependent`と週次`potDependentMeals`に記録。
- 初期食材充足とは独立の分類。食材由来の依存食数と重複するので合算しない。
- 新しい観測JSONは第5診断を保存する。旧3/4診断JSONを拒否せず、欠落のため比較保留。数値の不正・再計算時の変化も検出。
- 保存直後・JSON再読込・CLIが共通ルールを使う。R02の例外許可に鍋依存は追加しない。
- 食事内訳と警告欄へ表示。大規模UI変更は行わない。

## 外部一次資料と限界

[公式・2025/7/8のマイナン登場告知](https://www.pokemonsleep.net/news/323836363139383039363439353234373337/)は、
マイナスの鍋容量増加が次の料理に作用することを説明している（2026-10-21取得）。
これは発動の確率分布・週間成立率の参照ではない。上流計算器の推定抽選率を実測値へ昇格しない。
今回の判定は現行計算モデルの依存関係の監査であり、ゲーム内部抽選の修正ではない。

この診断が0でも精度合格ではない。選ばれなかった料理が別の抽選枝で作れる可能性、
失敗枝の食材残留・げんき・後続生産、料理チャンスの相関、完全週間分布は未解決。
任意の成功確率を導入せず、週間数値を補正しない。

# STEP 2 v0.2.26 — 料理成立判定における初期確定在庫・期待値依存の監査

日付：2026-10-17（JST）。**STEP2精度ゲートHOLD／STEP3未着手**。

## 問題
`chooseRecipe` は個体からの期待食材数が含まれる `inventory` を整数の実在庫のように用い、必要食材数 `<= inventory` なら確定料理として `meals` を増やしていた。例：リンゴ7.5個という「期待値」は、実際に7個以上揃った確率と異なる。「成立した料理」のUI文言も過剰な確定表現だった。

## 安全な今回の実装
- `initialOnlyStock`：ユーザー入力の初期食材整数在庫をコピー。通常のおてつだい・食材スキル・共有バッグから得られる確率的生産は一切加算しない。
- 実際にシミュレーターが選んだ料理の必須材料を `initialOnlyStock` から消費し、残高不足分を `expectedMandatoryUnits` として記録。必須材料を初期在庫だけで満たす計画を `initialCovered` として記録。
- 余剰投入が有効なら `expectedExtraUnits` に初期食材から賄えない追加投入量を記録。先行料理・投入分だけ確定在庫を減らし、後続21食へ引き継ぐ。
- 結果に `initialCoveredMeals` / `estimatedMeals` を加え、UIは「期待値モデルで料理を計上」と表記。各食事に必須材料の由来と確定在庫不足量を明示。
- **料理成功確率やエナジーを改めて計算したわけではない。** 既存の料理選択・げんき・エナジー期待値集計は維持。初期在庫のカバレッジは「シミュレーターが選んだ先行料理を計画どおり消費した場合」の条件付きの下限評価で、ゲームの全シナリオに対する厳密な成立保証ではない。

## 検証
1. 21食分を初期在庫150個で満たす固定レシピ
2. 初期在庫0で全食が期待値生産に依存
3. 初期6個と必要7個の不足量1
4. 初期14個で2食充足・3食目以降は不足
5. 余剰投入が初期在庫を消費しても必須・追加の由来を混同しない
6. レシピ未選択の表示・計数ゼロ
7. 自動レシピでの料理エナジーと7日内訳保存
8. UI起動試験で「期待値で計上」「生産期待値に依存」表示を確認（既存テスト更新）

## 未解決
- 確率分布による食材の**種類別整数在庫**と料理成立率
- 未成立だった世界での食材消費・料理げんき回復・スキルの再計算
- 21食全体の料理選択と確率的な在庫配分の最適化
- 満杯の共有バッグに伴う個体間の相関
- 実ゲームでの週間定量精度・Android Chrome実機性能

**結論：確率を捏造して数値化する代わりに、期待値を実在個数のように提示する誤認を改善した。自動テストとゲーム内計算精度の合格は別扱いで、STEP2 HOLDを継続。**

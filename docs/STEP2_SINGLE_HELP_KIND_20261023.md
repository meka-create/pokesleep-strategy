# STEP 2 M3 — 単一おてつだいの食材種類別回収を排他的分岐で処理（2026-10-23 / v0.2.71）

## 確認したP1：期待食材個数での種類別再配分

週間の `collect()` は、食材所持枠・共有バッグ空きが部分的に制約される場合に種類別の保有期待値を先に作り、各食材種類へ比例配分（`exactFood` 経路）、または順序付き期待値回収（通常 `receiveFood` 経路）を行っていた。これらは**1回の食材抽選で選ばれる種類は排他的**という既存モデル内の仕様を保持できない。

独立人工例：完成おてつだい1回、食材抽選確率100%、食材A×3とB×1がそれぞれ50%、個体の所持枠は10以上、共有バッグの空きは1。保持期待値はA 1.5、B 0.5の計2個。ところが実際の1回の抽選はAかBのどちらかだけなので、バッグに入る種類の期待値は **A 0.5、B 0.5**。従来の期待保有数に比例する場合は **A 0.75、B 0.25**、種類順回収ではさらに一方へ偏る。合計の期待回収1個は同じでも、**料理に必要な種類の在庫が誤る**。

これは既存数理モデル内の局所的なP1誤差の独立反例であり、ポケモンの真の食材抽選確率や実ゲーム週間の誤差率を測定したものではない。

## 修正

- `collectOneHelpIngredientKinds(rate,slots,carry,freeDistribution)` を追加。初めに `min(slot.count,carry)` 個を1種類だけ得るという**排他的な食材抽選結果**を保持し、整数の共有バッグ空き確率ごとに `min(held,free)` を計算する。各食材種類の回収期待値・保持期待値と合計を返す。
- 週間 `help()` が**空の通常ポケットからちょうど1回の通常おてつだい**を完了したときだけ、`oneHelpFood` に当該食材スロットと抽選率を記録。2回目のおてつだいで無効化。追加おてつだいは別ポケットなので混ぜない。
- `collect()` で共有バッグの確定整数空きが分かる場合にこの1回分岐を利用。v0.2.70の5匹共有バッグ `sharedPlan` が有効な場合は、当該個体の**回収直前の空き確率** `freeBefore` を使う。
- `foodJoint` 経路では種類別の合計回収と元の整数所持数分布による合計回収を突き合わせ、不一致なら例外。複数おてつだい・既に残っていた所持品の種類相関・整数でない共有バッグ空きは従来近似のまま。
- 診断 `exactOneHelpKindCollections` を追加。**アプリの入力・保存JSON形式・CSV16列は不変更**。既存の編成条件、睡眠固定、月曜4:00、料理21食、大成功設定、凍結M1参照値も不変更。

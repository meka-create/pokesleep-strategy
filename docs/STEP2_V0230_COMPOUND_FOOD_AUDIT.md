# STEP 2 v0.2.30 — 複数種類を同時獲得する食材確率分岐の監査

日付：2026-10-17 JST。**STEP2計算精度ゲートHOLD、STEP3未着手**。

## 解消する数学的問題
食材を同時に複数種類入手する1回のゲームイベントを、種類ごとの周辺確率だけに分解すると、相互排他的/同時獲得の相関が失われる。たとえば「リンゴ3個とミルク2個をセットで40%／何も得ない60%」なら、両方必要なレシピの成立確率は**40%**であり、種類別確率の積40%×40%=16%ではない。

## 新しい純粋API
`addCompoundIngredientOutcomes(distribution, outcomes, capacity, maxStates)`
- 入力 `outcomes` の各確率分岐に `items:[{ingredient,count}, ...]` の**明示順序付き**食材リストを指定できる。
- 抽選分岐の確率合計1、食材種類は既知19種、個数は1以上の整数。0個の結果は `items:[]`。
- 初期整数在庫分布の各確率状態と結果分岐を結合し、複数種類の追加食材を**同一結果枝**の中に保持。
- バッグ容量がある場合は分岐ごとに食材の受領順で実際の空きを更新し、受領可能な整数個数のみ在庫へ加算。`expectedAdded` / `expectedRejected` を返す。確率質量が不正ならエラー。
- 状態数最大4096。超過時は黙った切り捨てなしに失敗し、虚偽の料理成功確率を生成しない。
- v0.2.28の単種類抽選API、v0.2.29の連続料理APIは維持。

## 受領順序の重要性
容量4、初期リンゴ1、1回の抽選でリンゴ3・ミルク2の計5個を得る場合：
- リンゴ→ミルクの順で受領すると、結果は**リンゴ4・ミルク0**。
- ミルク→リンゴの順で受領すると、結果は**リンゴ2・ミルク2**。
両者の総個数は同じ4だが、料理成立率が変わる。したがって**ゲームの実受領順が未確認の場合、この順序を実ゲームの推定として勝手に使用してはいけない**。

## 新規検証8件

## 2. フェーズの意味（日時≠入力完了≠作戦採用）

| データ軸 | 値 | 独立した意味 |
|---|---|---|
| イベント選択 | `UNSELECTED / SELECTED` | 単一の対象イベントと開始週を明示確定したか。**過去のデモ週を本番イベントにしない** |
| ゲーム日時 | `BEFORE / DURING / ENDED` | **JST月曜04:00～翌月曜04:00**の対象イベント期間。対象週未選択なら判定不能 |
| イベント条件 | `MISSING / EDITING / CONFIRMED` | 値が取得候補だけか、編集中か、明示保存済みか。条件ごとの確定状態を維持 |

| 作戦 | `NONE / DRAFT / ADOPTED` | 未採用案と採用済み作戦を明確に区別 |
| 保留変更 | `NONE / CONDITIONS_DIRTY / INVENTORY_UPDATED / SLEEP_CHANGED` | 採用済み計画を変えず、再提案の必要性と旧提案失効を管理 |

上記は**内部状態だけ**。ユーザーへ「フェーズ名」ラベルや切替ボタンを常時表示するわけではない。

### 画面に出す主操作の優先順位（高々1つ）
1. **未選択イベント**：必要なら「イベントを選択」。確定していない目標・作戦を完成品として見せない。
2. **終了後**：保存済み作戦を閲覧するだけ。新規提案/採用は禁止。
3. **対象週の採用済み作戦あり**：今日の作戦を先頭。通常主操作**0**。条件/在庫/睡眠変更があれば控えめな「残り期間を再提案」（前提未確定なら再提案不可）を示す。
4. **開始前、未採用**：準備目標が中心。**週間作戦の提案は禁止**。必要に応じてイベント条件を確認/保存できる。
5. **開始後、未採用、必須イベント条件不足**：「イベント条件を設定」。不足理由を1〜2行表示し、必要項目に直接フォーカス。
6. **開始後、条件確定済み、食材在庫未保存**：「食材在庫を登録」（U2在庫へ直接移動）。
7. **開始後、条件と在庫が揃い、未採用**：「7日間の作戦を提案」→モーダルで確認→明示採用。
8. **終了済み・未採用**：「イベント終了」の簡潔な状態表示のみ。架空実績を出さない。

※ 採用後の睡眠設定は任意の副次操作。新しいドラフトの存在だけで採用済み作戦の通常閲覧を置き換えない。

## 3. イベント条件：準備と開始の役割を分ける（フォームは分けない）

**条件の編集場所はU3の1フォームのみ。時期に応じて注目させる項目を変える。**

### 準備期間に把握する情報
- 対象イベント1件・日本語イベント名・開始週/期間（1週間のみ）、開催フィールドが判明していれば選択、公開済みボーナス等。
- `nitoyon/pokesleep-tool` の `event.json` と日本語辞書 `src/i18n/ja/events.json` を参照。**取得した候補は選択・検証するだけで自動適用しない。** ボタン操作で明示反映→必要なら条件保存。取得失敗時はlast-known-good維持。
- 開催まで料理カテゴリが不明なら「未確定」のまま。**通常時はカレー・サラダ・デザートの各最大エナジーレシピを同優先度に備蓄**。重点対象の1〜2レシピが確定していればその対象を採用。実際の食材目標はバッグ・既存在庫・料理エナジー・スキル/鍋とイベント週パーティ運用を踏まえてF3で計算（同数固定は禁止）。
- 必要な開催フィールド・イベント倍率等が不明な段階で、イベント固有の最適値を「確定結果」として出さない。U2では表示可能な**暫定目標と確定目標を内部で区別**し、説明だらけにしない。

### イベント開始前後に確定する情報
- 料理カテゴリ、確定きのみ、必要なEX・開催条件、チケット・鍋/料理チャンス補正等、**実際の週間提案に必要な条件**。
- 必須条件を推定で埋めない。保存済みでも未確定フィールドがあるなら提案ロック。既知の値でも計算未対応なら「暫定」と「実計算可能」を混同しない。
- 事前に既に分かっている値を開始時に再入力させない。再入力が必要なのは未確定またはユーザー変更の値だけ。
- 鍋拡張+200・料理チャンス+70%は**準備用の固定試算前提**。イベント開始時の実績入力フォームは新設しない。試算条件が実際の達成値であると表現しない。
- イベント固有条件はU3。通常鍋/バッグ/フィールドボーナス等のプレイヤー固有入力はU4。
- **U4未開発の段階で確認不能な条件はロックが正**。UIモックは確定したフィクスチャのみ提案経路をテストし、未開発のU4が必要なケースを無理に合格としない。

## 4. 食材在庫を3種の状態から混同させない

### イベント前
- U2在庫タブで19種類を入力。空欄は0扱い、保存後は明示保存済み。**準備期間中は何度でも修正可能**。
- 記録には`eventWeek`, `savedAt`, `values`, `source`を保持。開始前の**最後の正常な保存**をイベント開始時点の在庫候補とし、初回保存値に固定しない。
- U2の備蓄目標は**必要な目標食材の数値**。現在庫・実イベント開始在庫と混同しない。

### イベント開始後
- イベント開始用の基準在庫（存在するなら**イベント直前の最新保存値**）と、**途中更新用の現在庫**は別スナップショットとして保護。基準在庫は途中更新で遡及上書きしない。
- イベント開始前に保存がなかった場合、後から入力した現在庫を「日曜実績」と捏造しない。初期状態は**記録なし**として扱い、今の在庫で未来だけ計算できる範囲を扱う。
- 現在庫更新はU2のみ。ユーザーがU3の閲覧から入った場合は`tab=inventory`で直接在庫画面へ。保存成功時のみ同じイベント週の「作戦へ戻る」を表示し、**自動移動しない**。
- U3へ戻ったときは在庫スナップショット変更を検出し、採用済み作戦を保持しつつ「残り期間を再提案」を提示。明示採用までは変更しない。
- **保存前の入力途中・保存失敗**を正常な新在庫として取り込まない。
- イベント週を変更しても前の週の初期/現在庫・採用済み作戦を流用しない。破損データはfail-closed、バックアップと旧キーの読み取り互換を維持。

## 5. U2・U3の具体的なタップ操作

### U2準備（既存デザインを最大限保護）
- 「準備目標｜食材在庫」の2タブ、19食材4列・必要数チップ・対象外グレー、準備スキルの小型ポップアップ。新しいステップ/大きな説明カードを追加しない。
- 通常目標閲覧：画面を開いて見るだけ。毎回の確認モーダル不要。
- 在庫保存：トーストで短く通知。準備期間中は「作戦へ」を**副次導線**にできるが「今すぐ週間作戦を提案」と偽表示しない。
- U3から在庫更新のために来た場合：**在庫タブを最初に表示**。同じ週を保持し、保存後「作戦へ戻る」を副次導線として提示する。戻り先はU3の当日閲覧。

### U3作戦：イベント開始前・未採用
- 必要な設定はいつでも確認できるが、未完成の週間作戦を出さない。準備目標への導線は小さく。
- イベント未選択/条件不足/在庫不足は**各1個の主操作**と短い不足表示だけ。条件が確定するたび次の操作が切り替わる。
- 睡眠編成は`睡眠編成｜自動OFF｜設定`のコンパクトな操作を維持（設定右端、ヒーラー配置も維持）。
- 本来の曜日・チームは採用後に表示し、未採用のデモ値を実績として見せない。

### U3作戦：採用済み・イベント中
- **第一表示は曜日タブ＋現在曜日の朝/昼/夜の3チーム・3食＋睡眠1晩**。全21枠を縦一列に出さない。
- 重要なアイコン・レベル・ステータスモーダルを維持。朝昼夜の**パーティと料理は参照専用**。
- 睡眠7晩の手動設定・未開始夜への一括コピー・自動OFF/ON・手動保存値保持を維持。自動ON/OFFだけで採用済み作戦を変更しない。
- 条件編集は小さな入口、唯一のパネルを展開したときだけ詳細を見せる。重要な今日の編成を常時下へ追いやらない。
- 在庫更新／再提案の導線は下段または変更検知時の1アクション。**毎日最初に巨大な再提案ボタンを表示しない**。
- JST04:00で初期曜日を選択。他曜日を手動閲覧中に勝手に戻らない。**1画面に4枠すべて収めるために画像や文字を読めないほど小さくしない**。先頭に曜日/第一枠を明確に表示し、必要なら下へスクロール。

## 6. 表示状態と画面遷移の技術設計

### 単一の判定ロジック
`getPrimaryViewState({selectedEvent,gameClock,confirmedFields,inventorySnapshots,adoptedPlan,draft,dirtyFlags})` のような**純粋関数**で、`phase`・`readiness`・`adoption`を別軸に判定する。出力`{screen,primaryAction,compactWarning,lockReasons,canPropose,canRepropose}`をU2/U3/U5から参照。

**内部主操作は一つ**：`SELECT_EVENT / SET_EVENT / SET_INVENTORY / PROPOSE / REPROPOSE / NONE`。これは自動状態であり、UIには必要な主操作が**0〜1個**出るだけ。睡眠設定等は副次操作。

### ナビゲーションの責任
- **E2〜E4（U2/U3単体）**：ユーザーがリンクを押した場合の遷移、保存済み状態の共有、戻り先を正しくする。ページの初期タブ・曜日切替はテストするが、**全アプリ起動時に勝手に別タブへ移動しない**。
- **U5（統合アプリ）**：作戦／準備／ボックスの共通タブ、同一オリジンの保存、アプリ**新規起動時**の自然なデフォルト画面（準備中は準備、イベント中は作戦）の導入。ユーザーが自分で移動した後はその閲覧/入力を奪わない。アプリ復帰・ブラウザ戻るで無意味な画面跳躍をさせない。
- **プレビュー**のURLには`eventStart`,`tab=inventory`,`return=plan`,`previewNow`（テスト専用）だけを画面文脈として持てる。ユーザー情報は必要に応じて**検証済みスナップショット**で受け渡す。ローカル`file://`でlocalStorageが共有されるとは仮定しない。
- **本番PWA**はU5の同一オリジン状態を正本にする。プレビュー用URLのイベント在庫JSON転送を本番の保存方式としない。長すぎる/破損/別週URLパラメータは拒否し、失敗を黙殺して旧値を新値と表示しない。

### 保存と変更
- 取得候補≠確定イベント条件≠編集中フォーム。保存して初めて確定。イベントの自動取得は**取得→検証→ユーザー明示反映→保存**。既存の日本語辞書とイベントソースを保持。
- U2現在の `pokesleep-strategy-u2-v3:<week>:inventory` とU3 `pokesleep-strategy-u3-v1:<week>`、旧CSV16列/JSONの互換を維持。新しい開始在庫・現在庫の構造は**新スキーマとして読み取り互換移行**し、移行前にバックアップする。
- 条件・在庫・睡眠チームが提案後に変わったら未採用ドラフトを無効化し、**最新条件で再提案**を要求。採用済み作戦は変更しない。
- 週途中再提案：過去／現在の時間帯と料理は固定、**次の時間帯から**残りだけ再探索。未記録の過去枠に架空の実績を付けない。
- イベント終了後は新規/再提案を禁止し、保存済みの閲覧を維持。

## 8. U3-DとU5/Fの受入シナリオ（失敗したら実機NG）

1. **未選択イベント**：デモ週や古いイベントを開催中と偽らず、必要ならイベント選択だけ促す。
2. **準備**：U2目標閲覧→食材在庫を入力/保存。開始前でも事前イベント条件を開ける。料理カテゴリ未確定で3カテゴリを同優先度に扱う（本計算はF3で精度確認）。
3. **開始・条件不足**：U3で未確定理由が短く分かり、条件パネル1つから編集/保存。EX/きのみ不足は推測補完なし。
4. **開始・在庫不足**：U3→U2食材在庫へ直行→0個も保存→同じ対象週のU3へ戻り提案可。戻り先で条件再入力なし。
5. **提案/採用**：週の自動提案→モーダルで7日閲覧→明示採用。提案をキャンセルしても旧作戦不変。
6. **毎日の閲覧**：イベント中の新規オープンは曜日ナビ＋今日の4枠が先頭。火曜03:59/04:00と水曜15:00、手動曜日閲覧中の保持、再読込を確認。
7. **途中在庫更新**：水曜U3→U2在庫タブ→保存→戻る→再提案→レビュー→採用。過去・現在枠と料理を固定し、採用前の旧作戦を変更しない。
8. **睡眠7晩**：自動OFF初期、曜日ごとの5匹変更、未開始7晩一括、ON後OFFの手動保持、ヒーラー右端配置。日中の個別編集は無し。
9. **状態変化/異常**：イベント週切替、終了後、ブラウザ戻る、URL異常、保存/読込失敗、取得候補不整合、ドラフトの条件古さ、初期在庫の誤上書き、別週混入を拒否。
10. **実機UI**：Pixel 7aと320/360/393/430pxの幅、タップ44pxを目安、フォーカス・独自プルダウン・モーダル、読みやすさを確認。**4枠の画面内完全収容は強制しない**。
11. **不要UIの不在**：毎日説明カード/イベント条件フルフォーム常時表示/フェーズ手動スイッチ/余計な比較タブ/昼21枠・料理編集/重複イベント入力を禁止。
12. **U5以降の再受入**：アプリ起動時の自然な入口、共通タブの操作、同一オリジン保存共有、ボックス実登録、実計算の適合性。UI単体のE6成功で完了扱いしない。

- 睡眠7晩の手動差分を消す、日中/料理の手動編集、パーティ/レシピ21枠の日中入力を要求。

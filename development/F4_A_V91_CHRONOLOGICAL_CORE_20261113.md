# F4-A v91：28枠の時間順参考最適化エンジン（2026-11-13）

## 対象と目的
- 基準：F4直前最終独立監査 v90、main `6318391a80bd3ebc48e469cb81839163657e26d4`、PR #181統合・2系統717件PASS・4 Actions SUCCESS。
- F4-Aは、**5匹×21日中枠（朝・昼・夜）、21食、7晩**の**連続した状態と在庫の時間順処理**を初めて実装する計算基盤。単なる7日固定チームや料理個数最多の試算ではなく、時間帯別編成候補と次に必要な料理に影響する食材在庫を同じ試算へ接続する。
- 実装は独立`f4/f4-chronological-core-v1.js`と実ボックス検証・基礎個体率の`f4/f4-f1b-roster-adapter-v1.js`。**E7の保存済み作戦・UI・保存データの変更はこの工程では一切しない**。F4-Bでブラウザ入力・UIへ読み取り専用で接続する。個人69個体CSVはpublic repoで使用せず、架空の検証用個体で自動テストする。

## 初期実装済みの連続処理
- 7日×`morning / noon / evening / sleep`の28枠を時系列で生成。21日中の毎枠では、**枠の開始時点の所持食材から料理候補を決めて消費した後**、選んだ5匹のおてつだいで食材・きのみを生産する。よって朝の食材生産を同日の朝食へ前借りしない。
- 同じ19種類の食材を全料理で共有・消費し、バッグ総容量を超える予測食材を保持しない。食材期待数は端数を保持（実際の確定獲得数ではない）。料理はレシピの**基礎エナジー**と明示されたフィールドボーナスだけを評価。鍋容量は通常、日曜日2倍、いいキャンプチケット1.5倍を基準とする。
- 日中パーティは限定候補チームから時間帯ごとに自動選択。料理候補は毎枠成立するレシピから高エナジー上位3件と「料理なし」を候補にして、残る週への食材温存も比較できる。ビーム幅18の**決定的な限定探索**で、全組合せ厳密最適解の保証はしない。
- 睡眠編成は`autoSleep:false`が既定運用。**7晩それぞれ手動指定した5匹**を自動変更しない。不足/重複・未対応個体があれば`BLOCKED`。明示`autoSleep:true`のみ夜間自動候補比較を行う。今の睡眠編成UIの架空12匹を**実ボックス個体として流用しない**。
- F1-Bの同一commit固定・合法ビルド検査を通った66種族フォームの**合法な全個体構成**を対象。性格・ミント・リボン・解放済みサブスキル・他の4匹のおてつだいボーナスでF1-Bの各個体の秒/おてつだい、1回の食材期待数・きのみ期待数を算出。きのみの1個のエナジーは既存F1-Cの`berryUnit`数式を参照し、レベル・指定フィールドボーナス・きのみ好みを利用する。
- 元個体のニックネーム・食材構成・個体識別子を結果へ返さない。参照ID`p0`等でチームを表現。F1-Bから`SPECIAL_REVIEW_REQUIRED`/不正個体・未対応フォームを適切に除外し、計算可能な5匹がなければBLOCKED。
- エネルギー試算対象：基礎のきのみ期待エナジー＋料理基礎エナジー。出力の`energyProxy`はあくまで`PROVISIONAL`。

## 意図的に未実装・次へ持ち越す条件
1. **最重要**：イベント補正は`eventSource`があれば**必ずBLOCKED**とする。`eventMode:'NEUTRAL_REFERENCE_ONLY'`を明示した実イベント非適用の参考計算だけ許可。v90で監査した11/16イベントの鍋+30・ナッツ+1・新3料理・2種類のエナジー1.5倍などは、データと式が揃うまで未対応とする。F4イベント網羅性ゲートを回避するものではない。
2. **時刻境界**：実ゲーム週は月曜04:00 JST〜翌月曜04:00 JSTだが、UIの朝07:30〜12:00/昼12:00〜18:00/夜18:00〜00:00/睡眠00:00〜07:30を7回並べる参考時間格子は月曜07:30〜翌月曜07:30をカバーし、**前後3.5時間のずれ**がある。F4-Bで前週末の睡眠引継ぎと04:00境界切断を接続するまで実ゲーム週の完全年間計算とみなさない。
3. **げんきとスキル**：F1-Bの0げんき基準速度のみを使用。げんき時間変動・回復・スキル抽選/ストック/料理チャンス/鍋拡張・所持枠/定期回収/交代直前の持ち越し、料理レベル、Extra Tasty、きのみ好みEXの不明補正は**未接続**。エネルギー合計を完成版として断言しない。F4-B/C以降でF1-Cのより正確な状態遷移を再利用する。
4. **生産量の確率**：毎枠の食材は期待値を連続で加算し、料理は現在の期待在庫で成立するか判定。実ゲームで「食材が確実に揃う」保障ではない。可用性を確率分布で評価するモデルはF4後半で接続する。
5. **実機UI接続**：F4-Aは独立計算のみ。E7の週間編成にはまだ反映しない。F4-Bの次工程で確定イベント条件・選択した7晩の実ボックス個体・現在庫を読み取り専用で注入し、イベントの不足補正が判明した場合は何も採用せず停止する。

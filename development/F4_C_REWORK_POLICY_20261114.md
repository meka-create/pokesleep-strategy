# F4-C 一体型改修・最終設計方針（2026-11-14）

## 決定事項・優先順位
この文書はF4-C v110のユーザー実機プレビューへの指摘を反映した**改修仕様の正本**。旧v110の「実ボックス専用カード」「手動で主・副ヒーラーを選択」「前週睡眠・7晩・きのみの二重入力」「了承チェック」「未採用の別計算」というUX方針は撤回する。v110実装は作り直しの対象であり、完成版UIの仕様ではない。F5には進まず、現行**19食材・78料理**の実ボックスを使うF4-Cを完成させる。新20/81要素は初回完成を阻害しない後続拡張とする。

## 既存E7 UIへの統合（新しいカードや設定画面を増やさない）
1. 既存「7日間の作戦を提案」ボタンから、登録済み実ボックス・保存済みイベント条件（きのみ、料理、確定済み補正）・保存済み食材在庫・プレイヤー設定を自動参照する。補助カード `f4c-real-card`、`f4c-real-consent`、主・副ヒーラー、好みきのみ、睡眠5匹の重複手動入力は完成画面から撤去。
2. 提案は既存の提案確認モーダル→「この作戦を採用」→既存の週間編成表示へ接続。曜日ごとの朝昼夜パーティ・料理に**実個体**を表示し、イベント所有IDと端末内の安定個体IDで採用・保存・復元する。旧デモ個体を新計算結果へ流用しない。未採用と採用済み、過去実績と予測結果を明確に区別する。
3. 睡眠編成は既存E7カードの自動ON/OFFに従う。ONはボックスの実個体から7晩を自動提案、OFFは既存の曜日別手動睡眠5匹を尊重。前週持越しは実際に保存・確定した情報を使用し、存在しなければ勝手に捏造せず、必要な確認は既存睡眠UI内で扱う。
4. 新規の「イベント補正未反映に了承」チェックは**完全撤去**。確認済み効果だけを自動適用し、未確認の補正・新食材/新料理は結果の短い注記（例：「一部イベント補正・新要素は未反映」）で伝える。ユーザーへ毎回同意を要求しない。知らない効果をゼロ確定として扱ったり、公式イベント完全エナジーと誤認させたりしない。中立モデルの計算範囲が妥当な場合は実個体編成を提示し、非対応部分だけ局所保留する。内部のイベントID・保存所有、完全計算と参考計算の分離、原典ゲートを保護する。

## 主ヒーラー・副ヒーラーの自動最適化（必須）
- **ユーザーは主・副ヒーラーを選ばない。** 66対象種族・フォームに属する全合法実個体を対象に、ボックス内の検証済みチーム全体回復スキル保有個体から主・副の異なる組み合わせを生成し、自由枠・料理・睡眠・時間帯との組み合わせで**週間の総期待エナジー**を比較して自動決定する。単にスキル回復量や発動確率が最大の個体を先に固定しない。合法なヒーラー2体が足りない場合には不足を示し、架空個体で穴埋めしない。
- ユーザーが確定した編成ルールを維持：朝は主＋副ヒーラーと自由枠3、昼・夜は主ヒーラーと自由枠4。主は右端、副は右から2番目。副が昼夜に自由枠として紛れ込む等、既存のチーム制約は保持。睡眠編成は別ポリシー。
- **ヒーラー自身のきのみエナジーも評価対象**。特にイベント開催フィールドの「好みのきのみ」とヒーラーが拾うきのみが一致する場合は、そのフィールドでの既知倍率を適用して候補を比較。きのみの数S、個体レベル、性格、おてつだい速度、サブスキル、ボーナス、きのみ基礎エナジーを既存の検証済み式で反映する。イベントによる好みのきのみの変更も**保存済み確定条件**を優先し、固定フィールドのデフォルトで上書きしない。好みのきのみ不明時に一致ボーナスを勝手に推定しない。
- 回復エナジーへの**間接効果**（げんき維持→手伝い回数増加）は、対象個体・パーティ全員の時間依存を可能な限り既存F4カーネルで再計算する。回復発動を実測と仮定して確定付与しない。未検証のスキル抽選はモデル仮定・期待値として明示し、確実な回復が発生したことにしない。
- ヒーラー自身の食材収集、メインスキルによる確認済み直接エナジー・料理支援、おてつだいボーナス等の全体補正も、参照原典と対応範囲内で反映。主・副2枠の採用によって高エナジー自由枠が失われる**機会費用**と、食材不足・料理変更による週間エナジー差も同じ探索で比較する。
- **得意きのみ一致のヒーラーが、回復性能はやや劣っても週間全体の期待エナジーを上回るケースを必ず評価可能にする。** 逆に、きのみが有利でも回復低下による全体損失が大きい場合は自動で選ばない。ヒーラーだけ別の優先順位や固定加点で単純選出せず、きのみ・料理・スキル・げんき効果の**二重計上を禁止**する。
- 速度優先方針に基づき探索は限定探索でよいが、組み合わせ候補が最初から回復性能順の単独候補に偏ることを禁止。少なくとも回復優位・好みきのみ一致・きのみの数S・チーム補正優位の候補系統を比較し、探索範囲・期待値前提の透明性を保つ。比較していない全組合せに対する「絶対最適」は標榜しない。

## 検証・受入条件（F4-C完了前に必須）
1. 好みのきのみ一致で高エナジーのヒーラーが勝つケース／不一致では回復優位ヒーラーが勝つケース／きのみの数S有無／スキル発動の期待値と実測混同禁止／おてつだいボーナスの二重加算防止を代表テストで確認する。
2. 朝主＋副／昼夜主のみ、自由枠、右側配置と7晩睡眠ON/OFF、前週持越し、29窓04:00境界、19/78料理と在庫制約が両立する。
3. ユーザーに主・副ヒーラーや好みのきのみを再入力させず、E7既存の提案ボタン・確認モーダル・採用保存・曜日表示のみで操作できる。追加カード・了承チェック・「作戦を採用できない」UXが残らない。
4. 保存/復元時はイベントID・条件改訂・在庫改訂・stable Box IDと合法個体を再照合。別イベント在庫やボックス並び替え・削除・同内容重複・複数タブ競合による誤参照を阻止。元69個体CSV/ニックネームを公開GitHubへ保存しない。
5. 既存E7受入済みUI、Pixel PWAアイコン、正式root切替時期を保護。PR最終形のCI2系統→mainのCI2系統/Pages、代表的な実機総合確認を実施。F5に着手しない。

## 実装の順番
**F4-C ① ヒーラー含む全自動探索と睡眠ON/OFF接続 → ② 既存提案ボタン/確認モーダルへ一体化しv110別カード撤去 → ③ 実個体stable IDの採用・イベント別保存/復元 → ④ UI・計算・保存の統合回帰/実機確認。**
①〜③は可能な限り同じ開発まとまりで実装し、未完成のUIを小出しにしない。F5へは進まない。

# M4 v135 — 準備の3カテゴリは週の料理タイプ別代替候補：重複食材の最大値統合（2026-11-28）

## Android実機報告と原因
Pixel 7aで作戦提案は成功。備蓄「集めておく食材」3カテゴリ、保存料理が
- カレー：とびはねるカレーうどん 1食
- サラダ：ごろごろねっとうサラダ 1食
- デザート：みつあつめチョコワッフル 1食

の場合、作戦室は322個、比較先の料理計画ツールは277個となる。**レシピの各食材必要数は両方同じ**。カレー112個、サラダ95個、デザート115個で固定原典も一致。
- **作戦室の旧計算**：3品を同時に食べると仮定した材料合算（キノコ31+27=58、コーン18+28=46、合計322）。
- **通常の1カテゴリ確定週の備蓄**：週の料理タイプはカレー／サラダ／デザートのいずれか1つ。3種類の料理は**代替候補**であるため、共通食材はカテゴリ別の必要数の**最大値**を確保する（キノコmax(31,27)=31、コーンmax(18,28)=28、合計277）。

比較先の料理計画ツール https://pokemon-sleep-tool-factory.vercel.app/meal-planner は、「週の始めにランダムで決まる料理カテゴリに備え、重複する食材は最大値で統合」と用途を明示している。各レシピの個別内訳はゲームエイトの2026-11更新ページ・E7の固定81料理データで照合。**322は3品を同時に作るなら正しい**ので、単純な数値の誤植ではなく、「備蓄」と「同時調理」の計画モード混同が実機不具合の本質。

## v135の修正
1. `f3/f3-stockpile-v120.js` に入力モード`ALTERNATIVE_WEEKLY_FOOD`を追加。各料理カテゴリの食数×レシピ需要をそれぞれ計算し、食材ごとに`Math.max(...各カテゴリの需要)`で目標を統合。実バッグ占有は従来どおり`Σ max(現在庫,目標)`で検証し、既存の不要な食材・現在庫もバッグ容量を消費する。
2. イベント週料理が単カテゴリ確定または未確定の場合、F3の表示・レシピ保存編集とF4/F5のバッグ検査に`ALTERNATIVE_WEEKLY_FOOD`を使用。**すべての料理カテゴリで作れるイベント**（`food==='all'`）では従来の`ALL_MEALS`（同時使用材料合算）を維持し、固定料理の判定を緩めない。
3. v133の保存済み3カテゴリ・レシピ・食数・Box・在庫は一切移行／上書きしない。週料理が1カテゴリのときF4/F5には適格カテゴリ1つだけを投影、他の備蓄は保持。カテゴリごとの上限はそれぞれ最大21食、すべて調理可能なイベントでは合算21食を維持。
4. U2準備の「備蓄目標」に`1/21食（3カテゴリ候補・最大値）`を表示、レシピ編集下部には`共通食材は最大値で確保（合算しません）`と説明。カテゴリ別の`1食`表示は従来のまま。
5. 旧v124の採用作戦の生産見込み控除は、**代替3カテゴリの場合は適用しない**。全3料理が実際に計画されたと誤認して予測控除しない。単一備蓄カテゴリ／全料理可能イベントの従来整合時のみ既存判定を使用。F5過去実績、PWAルート、Box/private CSVは無変更。
6. E7専用SWのキャッシュバージョンを更新して端末反映を確実にする。
